# PS1 static main-menu rendering

## Intent and boundary

The first PS1 menu milestone boots directly into the complete **initial main-menu screen**: logo, background, panels, labels, and selected-row styling. It is a visual milestone. There is no navigation, pointer or pad interaction, transition, scrolling, marquee, or animation. The authored menu in demodisc remains untouched, including its uncommitted work. The existing `cube_test` path remains available for regression builds; this milestone does not add a multi-scene catalog or a return path.

The target scene is the committed `assets/scenes/DemoDiscMainMenu.helen` from demodisc revision `5cc124eec06b8db729b2f9b15d99d26cb1ca8cc3` (blob `7bdb310b5169ebf2c68a394a850f9eacf13cda6a`). The current working copy of that scene contains only camera and logo, so using it would not satisfy the requested screen. The current demodisc assets and settings remain the other build inputs, including the PS1 texture adjustments. Their hashes and the shared engine revision are recorded for each build. No engine checkout or pin is moved.

## Approach

Use a build-local static export of that committed scene. A small wrapper reads the pinned Git blob as bytes into a fresh output under `C:\dev\helworks\builds\helengine-ps1`, verifies its blob identity, and invokes a dedicated `helengine.ps1.samplegen --static-menu` mode. The exporter deserializes the source scene, keeps the authored hierarchy, IDs, enabled states, transforms, camera, viewport, layout, clipping, sprite, text, and shape data, then removes the known runtime-only menu, item/panel controller, scroll, animation, marquee, and background-motion components. It applies the same filtering to scope-added components so an `sd/msd` override cannot reintroduce a stripped behavior during packaging. Any unclassified component type fails the export with entity, scope, and type; there is no silent drop. The export report records source revision/blob/SHA-256, output SHA-256, scene ID, component inventory and removals, and override scopes. The build report separately records hashes of the staged dependencies and the actual engine revision.

The alternative of authoring a PS1-only static menu in demodisc would fork presentation and disturb its dirty work. Making the whole interactive menu run now would expand this visual milestone into input, state, audio, and transition work. The build-local export keeps this first step small and reproducible while retaining the committed visual design.

The existing one-scene `build-authored.ps1` flow stages demodisc, replaces only `assets/scenes/DemoDiscMainMenu.helen` with the exported scene, and selects `DemoDiscMainMenu` as the startup scene. It must accept a scene whose report retains zero project scripts and prune runtime scripts accordingly; the old spin-component requirement applies only to the cube subset fixture. It does not overwrite demodisc files. The staged `settings/platform-groups.json` places PS1 in `sd/msd`, and the engine packager resolves those overrides as usual. The output report and packaged scene are inspected to confirm the visual components are present and the excluded components are absent after override resolution.

## Runtime behavior and resource limits

PS1 scene boot currently requires both a camera and a 3D drawable. Permit a camera with zero 3D drawables for this 2D menu, while still failing clearly for a scene with no camera. `Ps1RenderManager3D` then submits the 2D queue with the authored camera. Boot and frame diagnostics should report zero 3D drawables without implying a cube pose. This does not change cube rendering.

The static menu is expected to use more UI packets than `cube_test`. First build with the current packet budget and read the UI failure/high-water counters. Increase only the exhausted capacity, if necessary, using the measured packet count and a small documented headroom. Check the linked PS-X EXE, static RAM, heap capacity, runtime heap endpoint, and packet guards against the retail 2 MB limit. A memory or packet failure is a measured result to resolve, not a reason to remove panels or alter authored visuals silently.

## Failure handling and verification

The exporter fails for a missing or changed pinned blob, wrong scene ID, malformed scene, unknown component kind, or a behavior component surviving in any base or scope-added record. Tests deserialize the exported scene and check preserved entity IDs, parent/child relationships, enabled state, visual payloads, `sd/msd` overrides, and removal of behavior components in both base and override additions. Tests exercise a deliberately unknown component and a scope-added behavior component; they check the model and report, not source-code substrings. The normal `--full` export and `cube_test` build behavior must remain intact.

Build the menu with the actual shared engine revision recorded. Inspect the packaged scene, build manifest and linker memory figures. Guest logs must reach scene-ready and repeated frame markers with at least one camera, zero 3D drawables, nonzero UI work, no fatal marker, no UI failure, and intact packet guards; record packet high-water and heap readings. Run the relevant host tests, then a `cube_test` regression build if the packet budget or shared boot path changes. Ask before opening DuckStation. Once open, Helena confirms the main screen's logo, text, panels, colors, clipping and placement visually; logs alone cannot establish pixel appearance. Record measured results and evidence paths in `docs/Validation.md`, with no performance claim based only on the build.
