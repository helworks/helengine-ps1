# PS1 v0.1: video initialization and an unlit cube

**Status:** Design approved by Helena on 2026-09-15. Implementation handoff requested; no engine implementation started during planning.

**Goal:** Produce a small native Helengine PS1 executable that initializes video and reliably renders a rotating, unlit cube on the retail 2 MiB memory configuration.

**Confirmed scope:** Standalone native host first. Editor integration, generated runtime, and authored scene export follow in a separate milestone.

## Reference intake

Both supplied documents were read in full:

- [PlayStation 1 Development Handbook](../../playstation-1-development-handbook.md): startup/build workflow, memory limits, fixed point, rendering, frame ownership, debugging, and the wider platform roadmap.
- [PS1 Rendering Optimization](../../PS1_Rendering_Optimization.md): packet costs, GTE use, ordering, resource lifetimes, optimization priorities, and SDK provenance findings.

For this milestone, apply the handbook's sections 4–6, 8–11, 12.1, 14, 19.3–19.4, and 21–22, together with the rendering report's sections 2, 5–8, and 13. Their larger example scenes, streaming, lighting, and optimization programs are future guidance, not cube prerequisites.

The key conclusions are:

1. Use fixed-point geometry and SDK GTE helpers; do not carry desktop floating-point assumptions into the hot path.
2. The GPU draws screen-space commands. There is no hardware depth buffer; establish winding and far-to-near submission explicitly.
3. Packet storage must remain stable until transfer completes. A framebuffer must finish drawing before presentation. VBlank establishes neither of those completions by itself.
4. Account for code, data, BSS, SDK storage, heap, and stack inside retail RAM. Executable file size alone is insufficient.
5. Start with a repeatable scene and bounded storage. Assembly tuning, scratchpad specialization, and CPU/GPU overlap are later work.

## Foundation and alternatives

**Recommendation: C++20 with PSYQo/Nugget**, using its startup, GPU lifecycle, fixed-point math, and GTE wrappers. Keep PSYQo types inside the PS1 host/backend. Its `Application` owns execution and invokes one root `Scene`; the native host adapts to that lifecycle rather than creating a second frame loop. See the upstream [getting-started guide](https://github.com/pcsx-redux/nugget/blob/main/psyqo/GETTING_STARTED.md) and [concepts](https://github.com/pcsx-redux/nugget/blob/main/psyqo/CONCEPTS.md).

Alternatives:

| Approach | Benefit | Tradeoff for v0.1 |
|---|---|---|
| PSYQo, recommended | Existing C++ lifecycle and rendering support | Must adapt the host to its lifecycle and supported build route |
| Bare-metal support based on spicyjpeg's examples | Direct control over startup and GPU commands | More low-level ownership and synchronization code to maintain |
| PSn00bSDK | Broad APIs and CMake integration | Its README still identifies Sony-derived GTE assembly awaiting replacement |

The handbook recommends PSn00bSDK, while the rendering report raises the GTE concern. The current [PSn00bSDK README](https://github.com/Lameguy64/PSn00bSDK#to-do-list), checked during planning, confirms that concern. Prefer PSYQo for this new backend. Preserve notices for any reused components; use the bare-metal examples to explain hardware behavior.

Use Nugget revision `625da805c4a9bfd56dd9b2b17409805c0591dd42` as the initial source pin. Its build files, GPU lifecycle, allocator, primitives, and GTE example were subsequently retrieved directly while preparing the implementation handoff. Source availability is verified; compilation and execution remain untested. Bare-metal revision `33df9422bd5191def47f631b6fe2ffa647822502` remains a reference only.

## Visible result

- 320 × 240 progressive NTSC baseline, 15-bit RGB in 16-bit framebuffer storage, double buffered.
- A dark clear color and a centered solid cube rotating slowly around two axes.
- Six distinct, constant face colors: no normals, lights, textures, fog, or blending.
- A fixed perspective camera; no controller or external asset required.
- Eight unique local positions, twelve indexed triangles, and a color per face. Start with flat untextured triangle packets to keep winding and primitive construction simple.
- Backface rejection and far-to-near ordering. No software depth buffer.
- Rotation based on elapsed time using the SDK timer facility, with a bounded delta after debugger pauses. Do not advance by a fixed angle per displayed frame.
- Native rendering settings during validation: no enhanced resolution, geometry correction, extra RAM, or CPU overclock.

NTSC is the initial acceptance mode. A PAL configuration can follow once its display layout and timing are verified; do not silently select it and assume the same framebuffer layout or refresh rate. Equal-speed animation across regional modes belongs in that follow-up check.

## Geometry limits

Keep v0.1 deliberately limited to a fully visible convex cube. A suggested initial numeric convention is integer local coordinates of ±64, cube center at camera-space Z=512, projection distance H=256, screen center (160,120), and positive Z forward. Confirm axis orientation and winding against the selected SDK example before coding the mesh.

For any rotation, a cube of half-size 64 has bounding radius less than 111. Its nearest depth remains above 401, safely beyond a proposed near boundary of 160 and the H/2 projection threshold. Its conservative projected extent also remains inside the viewport. Verify these bounds using the actual quantized matrix path.

Use the SDK's fixed-point matrix representation and trigonometry. Compose the object-to-camera matrix once per frame. The initial face-at-a-time GTE path is sufficient for twelve triangles; shared-position caching is a later measured improvement. The eight indexed source positions do not imply an implemented transform cache.

The demo must detect an invalid pose or GTE projection overflow and report it without submitting malformed geometry. **General near-plane clipping is deferred.** `NCLIP` is a winding/area operation, not a polygon clipper. Before adding a movable camera or arbitrary scenes, implement bounded camera-space clipping; dropping crossing triangles is not the eventual solution.

## Structure and integration boundary

The inspected PS2 entry point delegates to `Ps2BootHost`, and the N64 draft uses a standalone host milestone. Follow that native layout, using namespace `helengine::ps1`, one class per file, and documented ownership. The existing `IPlatformAssetBuilder` contract concerns the separate managed content-build path and is not needed to prove native video.

| Proposed file | Responsibility |
|---|---|
| `src/main.cpp` | Create the PS1 application host and enter the SDK lifecycle |
| `src/platform/ps1/Ps1BootHost.hpp/.cpp` | PSYQo application adapter, ordered initialization, root scene ownership, startup diagnostics |
| `src/platform/ps1/Ps1CubeScene.hpp/.cpp` | Single PSYQo scene adapter, elapsed-time rotation, calls into the renderer |
| `src/platform/ps1/Ps1Video.hpp/.cpp` | Configure the SDK-owned GPU, document framebuffer layout and presentation contract; no second GPU instance |
| `src/platform/ps1/rendering/Ps1RasterRenderer.hpp/.cpp` | Camera/GTE setup, culling, depth buckets, packet generation and submission |
| `src/platform/ps1/rendering/Ps1FrameContext.hpp` | Fixed-capacity packets and ordering table, usage counters, ownership state |
| `src/platform/ps1/rendering/Ps1CubeMesh.hpp/.cpp` | Original immutable positions, indices, and face colors |
| `Makefile` | PSYQo build integration; executable, ELF, and linker map |
| `scripts/build.ps1`, `scripts/launch_in_emulator.ps1` | Windows entry points with explicit paths and propagated failures |
| `docs/Build.md`, `docs/Validation.md` | Reproduction instructions and observed validation results |

These are proposed files, not scaffolded interfaces. No C# builder, shared-engine API change, generated code, or placeholder subsystem is part of this milestone. Keep toolchain installs and outputs outside tracked source; use `C:\dev\helworks\builds\helengine-ps1` for build artifacts. Choose one supported host toolchain route during setup rather than implementing several at once.

## Memory and frame ownership

Two 320 × 240 framebuffers use 307,200 bytes, or 300 KiB, of VRAM. The pinned PSYQo implementation places them at (0,0) and (0,256), unlike the handbook's illustrative (0,240) second origin. Keep the SDK layout. No texture or font allocation is required for v0.1.

Use two fixed-capacity CPU frame contexts. An initial budget is 4 KiB packet storage and 256 ordering buckets per context. PSYQo stores 257 entries including its sentinel: 1,028 bytes per table and 10,248 bytes combined with both packet budgets, before counters. Twelve standalone flat triangle packets need only 240 bytes before clear/state/completion commands. Confirm actual structure sizes and alignment at build time.

Bounds-check packet reservation and depth-bucket access before writing. Capacity exhaustion is a diagnostic failure for this fixed scene, not silent geometry loss. Do not allocate per-frame heap storage. Reserve and account for the stack and any SDK heap usage, then verify allocated ELF ranges and reservations fit below `0x80200000` in the retail KSEG0 view.

Frame sequence:

1. Initialize diagnostics, the SDK GPU/display lifecycle, and GTE state in the supported order. Initialize both image buffers before displaying them.
2. Acquire a frame context only when the previous transfer no longer reads its memory.
3. Update rotation, configure the object-to-camera transform, and build commands for the non-displayed target. Clear precedes cube draws; completion follows them.
4. Transform, reject backfaces/degenerates, calculate bounded depth buckets, and emit opaque unlit triangles. Account for head-insertion reversal within equal-depth buckets.
5. Submit using PSYQo's documented mechanism. Keep packets, table links, and referenced state stable while in flight.
6. Let the SDK establish rendering completion and present at the intended VBlank boundary. Reuse resources only after their corresponding completion condition.

Start with conservative completion before reuse. Source inspection shows the pinned `GPU::flip()` waits for DMA transfer and a VBlank count change but does not explicitly wait for drawing completion or a new VBlank after completion. The implementation plan includes a narrow, tracked SDK patch inside that lifecycle to close both gaps; do not add a competing host display swap or queue. Reserve 64 KiB at the top of RAM for stack by overriding the allocator's `__stack_start` ceiling while preserving the SDK's actual initial stack pointer. Startup/projection/capacity failures must report a specific cause. Log boot checkpoints and the first completed frame, with no continuous normal per-frame printing.

## Milestone plan

### 1. Reproducible boot and video

- [ ] Inspect available compiler/container and `C:\dev\helworks\emus\ps1`; select one build route and emulator executable.
- [ ] Resolve SDK/compiler versions and build the matching upstream minimal example before adapting it.
- [ ] Add the native host, one scene, video configuration, and build/launch entry points.
- [ ] Produce `helengine_ps1.ps-exe`, a matching unstripped ELF, and a linker allocation map. A failed build must not launch a stale executable.
- [ ] Boot with PCSX-Redux and OpenBIOS, clear the screen, and verify repeated double-buffered presentation and startup diagnostics.

**Acceptance:** A clean build boots to a stable clear-color screen in retail-memory configuration, with known artifact and dependency versions.

### 2. Static unlit cube

- [ ] Add original cube data, camera/GTE setup, bounded frame contexts, and the flat triangle path.
- [ ] Verify winding first with one triangle, then render a fixed three-face cube pose.
- [ ] Enable backface rejection and ordering; keep lighting, blending, and texturing explicitly disabled.
- [ ] Check identity, quarter-turn, and oblique poses. Colors must remain constant as orientation changes.
- [ ] Inspect packet/depth counters and a diagnostic case of separated overlapping triangles at distinct depths. A convex cube alone does not prove ordering correctness.

**Acceptance:** Correct faces and constant colors at all diagnostic poses; no invalid packets or capacity failures; depth diagnostic draws the nearer triangle over the farther one regardless of insertion order into distinct buckets.

### 3. Rotation and robustness

- [ ] Add elapsed-time two-axis rotation and conservative resource reuse.
- [ ] Verify all supported poses satisfy the projection bounds; an intentionally invalid pose must produce a diagnostic rather than corrupted drawing.
- [ ] Exercise exact-capacity and overflow cases for packet storage, and the minimum/maximum permitted depth bucket. Use small host tests for portable arithmetic where useful and target checks for GTE behavior.
- [ ] Run ten minutes of rotation, including debugger pause/resume and repeated reset. Inspect tearing, hangs, missing faces, packet high-water marks, and memory growth.
- [ ] Verify the retail memory accounting includes BSS, frame contexts, SDK allocations, and stack/heap reservations.

**Acceptance:** Stable repeatable animation with bounded memory and no unexplained geometry loss. Record missed presentation intervals separately from time waiting for VBlank; emulator FPS is not a hardware performance result.

### 4. Reproduction and handoff

- [ ] Repeat a clean build and test missing-tool/build-failure diagnostics.
- [ ] Record artifact hash, source/dependency revisions, compiler, emulator/OpenBIOS version, video mode, memory evidence, and observed results.
- [ ] Test the executable on a retail PS1 through an available homebrew loader when hardware is available; record model and loader.
- [ ] Keep emulator validation and hardware validation as separate statuses. Hardware acceptance stays pending when no console is available.

**Acceptance:** Another developer can reproduce and run the standalone cube from the documented environment. Direct executable loading is the v0.1 delivery path; disc boot and asset loading are separate work.

## Deferred work and next milestone

Defer editor/generated-runtime integration, scene serialization, mesh import, textures, lighting, controller input, audio, saves, CD image packaging/streaming, UI, arbitrary-scene clipping, visibility systems, dynamic allocation frameworks, and assembly optimization.

After native bring-up, plan the narrow Helengine integration: one authored camera, transform, cube mesh, and unlit material routed through the existing managed build contract. Assess generated-runtime memory and numeric compatibility before promising a full engine port to 2 MiB.
